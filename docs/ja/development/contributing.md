# コントリビューションガイド

このドキュメントは、共同開発時の基本ルールを定義します。

## 前提

- `src/` はサポート対象 workflow の implementation of record である
- `legacy/` は archive-only であり、通常の execution surface として扱わない
- `en/` と `ja/` のドキュメントツリーは整合させて保つ

## 大きな変更を始める前

次の変更では [`../specs/`](../specs/) に spec を書いてください。

- 新しいワークフローを導入する
- 公開 CLI 挙動を変える
- データ形式を変更する
- 複数モジュールや複数人に影響する

次の変更では [`../adr/`](../adr/) に ADR を書くか更新してください。

- アーキテクチャ境界を変える
- 影響範囲の大きい依存関係を導入する
- モジュール間依存のあり方を変える
- 長期的な技術判断を正式化する

## ブランチとプルリクエストの期待値

- プルリクエストは一貫してレビューできる大きさに保つ
- 可能ならアーキテクチャ変更と機械的移行を分ける
- プルリク本文に関連 spec と ADR を明記する
- 挙動や構造を変えたら同じ変更で docs も更新する

## コードレビューで確認すること

レビュー時は次を確認します。

- [`../architecture/module-boundaries.md`](../architecture/module-boundaries.md) に沿っているか
- 変更リスクに見合うテストがあるか
- ドキュメント更新が入っているか
- `legacy/` との関係や移行影響が明確か

## ドキュメント運用ルール

- オンボーディングや導線を変えたら [`../../ja/README.md`](../../ja/README.md) と [`../../en/README.md`](../../en/README.md) を両方更新する
- 構造や運用ルールを変えたら `en/` と `ja/` の対応文書をそろえて更新する
- README を巨大な総合資料にするより、焦点の絞られた文書を追加する
- パッケージ構造、ワークフロー境界、移行経路に関わるコード変更をしたら、対応する architecture/spec docs も同じ変更で更新する

## テストルール

- domain ロジックには unit test を追加する
- I/O や CLI 配線には integration test を追加する
- 複数層にまたがる主要フローには end-to-end test を追加する
- root Poetry 環境では `poetry run srs-test` を使ってテストを実行する
- 層ごとの詳細ルールは [`testing.md`](testing.md) に従う

## 新規作業の基本配置先

- 新しい本実装コードは [`../../../src/`](../../../src/) 配下に置く
- `legacy/` 変更は参照実装の修正、同等性確認、避けられない保守に限る
- `legacy/` から挙動を移すときは移行意図を docs で明記する
